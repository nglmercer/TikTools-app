Couches de l’interface et circulation des données ​

Objectif et prérequis ​

Étendre l’application Vue sans coupler une page à l’IPC natif. L’interface utilise Vue 3.5, Pinia 4, Vue Router 5 et vue-i18n 11 selon les plages de l’espace de travail installé. Utilisez les dépendances verrouillées et les commandes de configuration plutôt qu’un nouveau squelette d’interface.

Trouver la couche responsable ​

L’organisation Feature-Sliced Design actuelle se trouve sous src/web/ :

CoucheResponsabilitéExemple existant
appInitialisation, routage, structure et durée de vie de l’exécutionapp/model/use-app-runtime.ts
pagesComposition des routespages/automations/ui/AutomationsPage.vue
widgetsPanneaux composés substantielswidgets/live-feed/ui/LiveFeedPanel.vue
featuresOpérations utilisateur et leurs brouillonsfeatures/apply-rule-template/
entitiesStores métier et logique métier réutilisableentities/rule-template/
sharedAPI, primitives d’interface, i18n et utilitaires génériquesshared/api/control-client.ts

Composez les couches supérieures à partir des inférieures. Gardez les appels hôte derrière le client de contrôle partagé ; le choix du transport appartient à l’initialisation. Les anciens emplacements src/web/platform et src/web/views des articles précédents sont historiques.

Implémenter une modification ciblée ​

  1. Repérez la route dans app/router/routes.ts, puis suivez sa page vers la fonctionnalité et le store d’entité.
  2. Utilisez un composant partagé existant pour les champs, états ou boîtes de dialogue. Préservez ses libellés, son comportement de focus et son contrat d’événements.
  3. Séparez les propositions modifiables des enregistrements sauvegardés de l’hôte. Utilisez shared/lib/request-scope.ts pour ignorer les réponses asynchrones obsolètes ; l’invalidation n’annule pas une mutation acceptée par l’hôte.
  4. Ajoutez les clés de langue via shared/i18n et libérez les abonnements à la fin de leur durée de vie propriétaire.

Résultat attendu, état et récupération ​

La route affiche les données actuelles de l’hôte et conserve les modifications non enregistrées en cas de conflit. Rankings dispose d’un code source et d’une route mais reste masqué dans la navigation normale ; ne déduisez pas la disponibilité produit de la présence d’un composant. Les initialisations native, navigateur local et démo peuvent fournir des transports différents tout en utilisant le même code de fonctionnalité.

Si une réponse obsolète remplace une requête plus récente, vérifiez sa génération avant de modifier le serveur. Si une route perd sa page de plugin, revenez à la vue des plugins installés comme le fait déjà l’exécution. Le runtime de l’application est la référence pour le rattachement, la resynchronisation et le nettoyage.

Détails de fonctionnement ​

Bootstrap choisit le ControlClient réel/demo ; mountWorkspace({client,locale,target}) installe Pinia, i18n, router et controlClientKey ; AppShell lance abonnements/resync des gaps et présentation via useAppRuntime. useControlClient échoue sans fournisseur même avec Pinia/i18n. Réutilisez la factory ou fournissez le client en test ; démontez et detach à la fin. Les entities ne choisissent pas le transport.

Avant await, créez ticket et sortie d’activité. Appliquez la réponse seulement si le ticket est courant ; sortez en finally. Invalidez au changement de contexte/démontage. Chaque opération superposée a sa sortie pour ne pas effacer le busy d’une autre. Invalider un ticket n’annule pas le travail distant.

ts
import { createRequestScope, createActivityCounter } from '@/shared/lib/request-scope.ts';
const requests = createRequestScope();
const activity = createActivityCounter();
async function refresh() {
  const ticket = requests.begin();
  const leave = activity.enter();
  try {
    const result = await client.call('system.info', {});
    if (ticket.isCurrent()) info.value = result;
  } finally { leave(); }
}
