# TikTools 4.2.1-rc.2 {#tiktools-421-rc2}

## Goal, status and prerequisites {#goal-status-and-prerequisites}

Use RC2's historical notes to understand the correction for concurrent Changes reads reproduced in RC1. The candidate record covers Linux AppImage, DEB and portable packages built locally while Actions was disabled. It does not establish current download availability or a newly built Windows package. Choose assets from the [release list](https://github.com/nglmercer/TikTools-app/releases), retain their checksum file and test with an isolated profile.

Cloud recovery and collaboration remain experimental. Nickname search still depends on backend `6a69c99` and migration `20261113000001_remote_invitation_recipients.sql`; the application package does not deploy those changes.

## Correction and expected behavior {#correction-and-expected-behavior}

Changes/conflict lists and protocol selection share protocol observation instead of reserving the product mutation slot. Toolbar and panel reads can complete while an unrelated package journal operation occupies that slot. Write fences, account isolation and explicit migration decisions remain.

The account check rejects logout, pending transitions and replacement sessions. Reading a local comparison does not restore credentials or start a Cloud request. On failure the UI shows the native reason and a local reload action; this retry does not send, download or resolve a record.

## Check the candidate {#check-the-candidate}

1. Record the displayed `4.2.1-rc.2` version and open Plugins → Changes in an isolated profile.
2. Open or reload the comparison from the toolbar and panel. A load failure should retain its reason rather than report that everything is synchronized.
3. Use the local retry and confirm that it reloads the comparison without changing pending queues or applying remote records.
4. Record account/session transitions separately. Compare with [RC1's migration procedure](4.2.1-rc.1.md) when reproducing an affected profile.

## Recorded validation and recovery {#recorded-validation-and-recovery}

The original record describes a deterministic 32-reader regression, CloudAuth/sync/native/frontend checks, and startup of the optimized AppImage with an empty isolated profile. Installer content and portable archive checks were recorded. That startup did not test signed-in production synchronization or media playback.

The historical AppImage SHA-256 was `35fc26e7bc5875c5a3fe99bf6a84baf77af8ca63d1c8b8e61825881187d6091f`. It identifies that recorded file; use the checksum attached to the asset you actually download.

If loading still fails, keep the version, native error and request ID, then use [Diagnostics](../user/preferences/troubleshooting.md). Preserve pending edits and conflicts. At RC2, Automations still used a local reference, Variables and Overlay section work was unfinished, and the historical SQLite lock holder remained unidentified. These notes do not assert that an older backend's missing people-search route has since been deployed.
