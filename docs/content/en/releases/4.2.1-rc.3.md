# TikTools 4.2.1-rc.3

## Goal, release status and prerequisites

RC3 is a published prerelease, as reported on 13 November 2026. Use it to evaluate the Linux desktop changes following RC2, with a backup and a separate test profile. It is a candidate rather than a stable-channel update. Download the published AppImage, DEB or portable asset and its `SHA256SUMS.txt` from the [release list](https://github.com/nglmercer/TikTools-app/releases); the recorded packages were built locally.

Cloud section recovery and collaboration remain experimental. The installation does not deploy backend migrations or establish production account compatibility.

## Changes available in RC3

- Retains RC2's correction for concurrent comparison reads and local retry with the native failure reason.
- Variables persist text, number, boolean, list and local-secret types. Atomic saves reject a changed host or stale editor revision, preserving existing template text rendering.
- Secrets remain masked. Switching hosts cannot fall back to a legacy write, and native classification excludes values queued before they became secret from later publication and comparison output.
- The native Variables bridge supports cached comparison, explicit one-variable adoption and cache-only download. Application rechecks session, consent, local revision and cache entry.

Saving Variables remains local. RC3 does not expose the complete Variables Changes button with reviewed send/withdraw and pending-conflict handling; that section integration is described in [4.2.2's source notes](4.2.2.md). Marking a local value secret does not erase a previously published Cloud copy.

## Check the published candidate

1. Verify the package checksum and displayed `4.2.1-rc.3` version. Keep test profile and XDG directories separate from your normal profile.
2. Create a harmless text variable such as `demoGreeting = "Hello"`, save and reload it. Check the other explicit types with non-sensitive sample values.
3. Open Changes and exercise loading/local retry. Inspect Settings/Teams and optional guided help without treating missing backend capabilities as successful setup.
4. Report the exact action, version, native reason and request ID for any failure. Keep tokens, invitation codes and secret values out of reports.

## Expected result, evidence and recovery

Typed local values should survive reload, while stale-host or stale-revision edits fail visibly. The original record reports native Variables/sync/parity checks, fake-host browser tests, sandbox CLI verification, installer content checks and frontend-ready startup with an empty isolated profile. It does not demonstrate signed-in production sync or media playback.

The recorded AppImage SHA-256 is `4b11260836457350debf2680b230c52cea8408ddf17ccdc729d0025a62149b7e`; verify the checksum file accompanying your download. On failure, preserve the copied profile and use [troubleshooting](../user/preferences/troubleshooting.md) before retrying recovery actions.

Nickname invitations depend on backend `6a69c99` and migration `20261113000001_remote_invitation_recipients.sql`. The old record observed a missing people route; no new production probe is claimed here. Automations Cloud transport, Overlay revisions and the remaining collaboration audit were unfinished, and the historical SQLite lock holder remained unknown.
