# ランキングと競技を理解する {#understand-rankings-and-competitions}

## 目的と前提条件 {#goal-and-prerequisites}

適切な順位表示を選び、開発中のランキング画面の制限を理解します。意味のあるスコアにはイベントの受信が必要です。現在の視聴者を確認するだけなら、通常の [ポイント](rules.md) の順位表や [ライブフィード](../live/feed.md) の上位視聴者パネルから始めます。

## 適切な表示を使う {#use-the-right-view}

1. **ポイント** で視聴者を検索し、ポイント、レベル、視聴者 ID で並べ替えます。手動調整と付与を比べる前に更新します。
2. **ライブフィード** の順位パネルを確認します。ポイント残高表とは独立してランキングエンジンのスナップショットを受け取る場合があります。
3. オーバーレイでは [オーバーレイ](../overlays/index.md) のランキング種別を選び、ソースの設定を確認します。出力には設定済みランキングソースが必要です。

専用の **ランキングとコンテスト** 画面は実験段階です。ルートは `#/rankings` ですが、メインナビゲーションには意図的に表示せず、起動タブとしても復元しません。サイドバー項目がなくても、ルートやエンジンが削除されたわけではありません。

## 実験的ランキングを設定する {#configure-an-experimental-ranking}

画面が利用できる環境では、配信者1人、ルーム1つ、ユーザー単位のグループ化、セッション期間で始めます。`tiktok.like` / `like.count` など提供されている指標を1つ、重み `1` で追加します。結果件数を控えめにして定義を作成します。フォームは移動期間と日次期間にも対応し、期間・イベント数の上限やタイムゾーン差を明示できます。

ソースを増やす前にスナップショットを読みます。一時停止・再開はランキングの収集に作用し、リセットは意図的にランキング状態を消します。競技の設定と投票関連ソースには独自のグループ化規則があります。ポイントのリセットで競技もリセットされる、またはすべての独自グループが全指標で使えるとは考えないでください。

## 期待される結果と提供状況 {#expected-result-and-status}

通常の順位表は利用でき、専用管理ページは実験段階です。スコアはホストが計算し、表示フィードの行数から算出しません。このガイドは実配信・OBS の動作や競技の全組み合わせを確認するものではありません。

## 問題が起きたとき {#recovery}

空のスコアでは配信者、ルーム、ソースの有効状態、期間、一時停止を確認します。非対応のソース・グループの組み合わせは架空のフィールド名で補わず削除します。リセット前に重要データを[バックアップ](../preferences/backups.md) し、報告には定義 ID と診断コードを含めます。
