# 共同操作とチームアクセスを準備する {#prepare-collaboration-and-team-access}

## 目的と前提条件 {#goal-and-prerequisites}

所有者の管理権を保ち、別の操作担当者に範囲を定めた役割を付与します。対応デスクトップホストを用意し、ローカル・ネイティブ共同操作か、アカウント方式のチームかを意識して選びます。チームには [Cloud サインイン](account.md) と対応する配置済みサービスも必要です。まず本番以外の構成と読み取り専用権限で始めます。

## 所有者側のアクセスを設定する {#configure-owner-access}

1. **設定 → 共同作業** で接続状態を確認し、操作欄から対象のリスナーまたはゲートウェイを有効化・設定します。
2. 招待作成前に許可オリジンとアクセス行列を確認します。担当者に必要な領域、操作、リソースだけを選びます。
3. 招待を作り、非公開のリンク・トークンを信頼できる経路で渡します。招待は承認済みの有効なセッションとは異なります。
4. 保留中の要求と要求された権限を確認します。想定した担当者だけを承認し、表示された本人情報と接続を確認します。
5. アクセスインスペクターで後の権限変更を確認します。不要になった招待、ID、セッションは取り消します。

委任された定義編集、所有者としての定義採用、委任実行の承認は別の判断です。各確認画面で保存済みソース、参照アクション、権限を読みます。定義のプレビューだけでは実処理は許可されません。

## アカウント方式のチームを準備する {#prepare-an-account-based-team}

**設定 → チーム** が利用できる場合、名前付きチームを作成して選択します。識別しやすい端末名で **このPC** をホスト登録し、**提供を開始** を使ってリンク状態を確認します。作成とローカルホスト登録はフロントエンドに接続済みですが、仲間の招待とは別操作です。コントローラー端末には独自の登録役割があります。

宛先、役割、招待の有効期間を選び、受信要求、メンバー、端末を確認します。ニックネーム検索には別途配置されたバックエンドが必要で、現在のサービスでは使えない場合があります。検索失敗だけで未登録と判断せず、選択を迂回するために任意の ID を代入しないでください。

## 期待される結果と提供状況 {#expected-result-and-status}

所有者のアクセス制御と、フロントエンドのチーム作成・登録は実装されています。リモート共同操作全体は実験段階です。実際の2台の PC での LIVE、本番のニックネーム検索、NAT・リレーの挙動、全プラットフォームと実処理の復旧経路はここでは確認されていません。リンクが準備完了でも、目的の操作について全経路で権限が守られるとは証明できません。

## 問題が起きたとき {#recovery}

権限やホストのリビジョンが古ければ再読み込みして再確認します。未確認コマンドは再試行前に記録済み結果を調べます。終了時は提供を停止するかアクセスを取り消します。招待トークンと認証情報を公開の[診断レポート](../preferences/troubleshooting.md) に含めないでください。

## 運用の詳細 {#operational-details}

Teams 参加・承認後も host が現在版のネイティブ権限を確認します。`pendingHost` は未完了で、接続や所属だけではアクセスできません。権限変更後に再読し host/端末を確認します。observer は読み取り中心、moderator は限定運用制御、automationEditor は限定編集、custom は明示レビュー済み policy が必要です。無制限 script・外部効果は付与しません。拒否理由が UI で不明なら[role と確認契約](../../developer/collaboration.md#operational-details)を参照します。
