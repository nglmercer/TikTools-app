# TikTools 4.2.1-rc.1 {#tiktools-421-rc1}

## 目的・状況・前提条件 {#goal-status-and-prerequisites}

この過去の候補記録を使い、RC1 で調査した Cloud 復旧、チーム、Linux AppImage の問題を再現します。対象はアプリ基準 `338495a9` と別のバックエンド基準 `6a69c99` です。現在 RC1 を取得できることは示しません。インストーラーを選ぶ前に[公開アセット](https://github.com/nglmercer/TikTools-app/releases) を確認します。

記録された候補は Actions 無効中にローカルで作った Linux AppImage、DEB、可搬型パッケージを使いました。新規 Windows インストーラーは含みません。移行テストにはバックアップと影響プロファイルの分離コピーを用意します。共同操作と Cloud セクションの復旧は実験段階です。

## この候補の変更 {#changes-in-this-candidate}

- 設定はアカウント・セッションと診断を保持し、プラグインがカタログ、検索、変更、インストールを担当します。テンプレートとプロファイルは自動化にあります。
- 共有変更パネルは比較失敗と正常な空結果を区別します。プラグインの送信は自身の選択・設定だけを送り、他の待機列と取得キャッシュを保ちます。
- 移行は暗黙の同梱プラグインディレクトリがなくても許容し、明示パスは厳密に扱い、不足パッケージ ID を示して確認付き修復を行います。保留編集と競合を保持します。
- チームはこの PC のホスト登録と別 PC のホスト選択を区別します。ニックネーム招待は選択宛先に結び付き、所有ホストの承認も必要です。
- 任意の操作ガイドは設定状態に従います。Linux パッケージは以後のメディア確認用に WebKit ヘルパー、GStreamer プラグイン、scanner を同梱します。

## 再現して期待結果を調べる {#reproduce-and-inspect-the-expected-result}

1. 表示バージョンと OS を記録します。プラグイン → 変更を開き、読み込み失敗なら正確なエラーと要求 ID を保持します。
2. コピーしたプロファイルで移行をプレビューし、修復前に不足 ID を確認します。修復後も再プレビューし、保留編集と競合が残ることを確認します。
3. チームで現在の PC を登録してから「提供を開始」を試します。別 PC のホストを選んでも、この PC の起動権限は得られないはずです。
4. AppImage 起動と音声・映像を別々に確認します。画面まで到達してもメディア再生成功の証拠にはなりません。

ニックネーム検索と宛先固定招待にはバックエンド `6a69c99` と移行 `20261113000001_remote_invitation_recipients.sql` が必要です。候補のインストールではバックエンドは配置されません。

## 復旧と証拠の制限 {#recovery-and-evidence-limits}

比較失敗ではネイティブの理由を残し、対応パネルから再試行します。保留状態を消したり、互換性検査から移行成功を推測したりしません。[トラブルシューティング](../user/preferences/troubleshooting.md) に従い、版、操作、秘密除去済み診断を集めます。

原記録は基準時点のフロントエンド、同期エンジン、宛先分離、2ホストのネイティブ・リレー検査を報告します。日付のある検査で、現在の本番検証ではありません。過去の SQLite ロック保持者は特定されていません。RC1 では変数とオーバーレイの Cloud アダプターは未完了で、自動化はローカル基準と比較していました。後の範囲は[後続候補](4.2.1-rc.3.md) と[現在の変更ガイド](../user/cloud/changes.md) を読みます。
